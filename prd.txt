# PRD — Cloud Backend ARISA

## 1. Ringkasan Produk

ARISA adalah sistem hybrid berbasis Raspberry Pi + aplikasi pengguna + cloud backend. Cloud backend menjadi pusat identitas, sinkronisasi, penyimpanan data utama, kontrol akses, log audit, notifikasi, dan integrasi AI cloud. Raspberry Pi berfungsi sebagai edge backend lokal yang tetap bisa melayani pengguna saat internet tidak tersedia, lalu melakukan sinkronisasi ke cloud ketika koneksi kembali tersedia.

Dokumen ini mendefinisikan PRD lengkap untuk membangun cloud backend ARISA dari nol sampai siap produksi.

---

## 2. Latar Belakang dan Masalah yang Diselesaikan

Sistem ARISA membutuhkan backend yang mampu menangani tiga kondisi utama:

1. **Online–Online**: aplikasi dan Raspberry Pi sama-sama bisa terhubung ke cloud.
2. **Offline–Online**: pengguna tidak punya internet, tetapi Raspberry Pi tetap bisa melayani secara lokal dan sync ke cloud nanti.
3. **Offline–Offline**: pengguna dan jaringan publik tidak tersedia, tetapi device lokal masih bisa beroperasi berdasarkan credential yang sudah pernah di-bootstrap sebelumnya.

Masalah utama yang harus diselesaikan cloud backend:

* memastikan identitas user dan device tetap aman
* menyimpan data utama secara terpusat
* menangani sync dari data lokal yang tertunda
* mencegah duplikasi dan konflik data
* menyediakan API yang stabil untuk aplikasi dan Raspberry Pi
* memantau kesehatan device dan sistem

---

## 3. Tujuan Produk

### Tujuan Utama

Membangun cloud backend yang:

* menjadi sumber kebenaran utama untuk user, device, dan data
* mendukung pairing perangkat Raspberry Pi ke akun user
* menerima sinkronisasi data dari local backend
* menyediakan API yang aman, terdokumentasi, dan scalable
* mendukung AI cloud sebagai fallback / augmentasi dari AI lokal

### Tujuan Operasional

* menyediakan onboarding user dan device yang simpel
* memungkinkan aplikasi ARISA beralih mulus antara cloud mode dan local mode
* menjaga integritas data walaupun koneksi internet tidak stabil
* menyediakan observability untuk audit, monitoring, dan debugging

---

## 4. Non-Tujuan (Non-Goals)

Cloud backend ini **tidak** mencakup:

* pengembangan model AI lokal di Raspberry Pi secara detail
* desain UI/UX aplikasi mobile secara penuh
* firmware rendah-level Raspberry Pi
* produksi hardware enclosure, UPS, atau sistem pendingin
* integrasi ke sistem pihak ketiga di luar kebutuhan inti ARISA

---

## 5. Prinsip Desain Produk

1. **Cloud sebagai sumber kebenaran utama**.
2. **Local backend sebagai edge buffer dan authority sementara**.
3. **Offline harus tetap aman, tetapi tidak boleh menciptakan identitas baru secara liar**.
4. **Semua data yang penting harus punya ID unik dan timestamp**.
5. **Sync harus idempotent** agar pengiriman ulang tidak merusak data.
6. **Security by default**: token, signing, audit log, dan revocation.
7. **Observability first**: tidak boleh ada komponen yang buta.

## 7. Use Case Utama

1. User mendaftar dan login ke ARISA.
2. User melakukan pairing Raspberry Pi ke akun.
3. Raspberry Pi mengirim telemetry ke cloud.
4. Raspberry Pi menyimpan data lokal ketika internet putus.
5. Cloud menerima sinkronisasi saat internet kembali.
6. Cloud memproses data utama dan menyimpan hasil final.
7. Cloud mengirim notifikasi status device atau hasil analisis.
8. Admin dapat melihat status device, log, dan histori sync.

---

## 8. Arsitektur Sistem Tingkat Tinggi

### Komponen

* **Client App**: aplikasi pengguna ARISA.
* **Cloud Backend**: pusat autentikasi, data, sync, dan AI gateway.
* **Edge Backend (Raspberry Pi)**: server lokal, queue, cache, validasi lokal, local AI.
* **Database Cloud**: penyimpanan utama.
* **Object Storage**: penyimpanan file, gambar, hasil model, lampiran.
* **Message Queue / Job Queue**: antrian job async.
* **Monitoring Stack**: log, metrics, tracing.

### Alur Besar

* App login ke cloud.
* User pairing device.
* Device mendapat identitas dan trust.
* Data mengalir ke local backend atau cloud tergantung kondisi.
* Local backend menyimpan data saat offline.
* Sync service mengirim data lokal ke cloud saat koneksi tersedia.

## 9. Ruang Lingkup Cloud Backend

Cloud backend minimal harus menyediakan 8 domain besar:

1. Authentication & Authorization
2. Device Registration & Pairing
3. Data Ingestion & Sync
4. Core Data Storage
5. AI Gateway
6. Notification System
7. Monitoring & Audit
8. Admin & Management Tools

---

## 10. Functional Requirements

### 10.1 Authentication & Authorization

Cloud harus mendukung:

* register user dengan email/password
* login user
* login Google/OAuth
* refresh token
* logout
* revoke session
* role-based access control

#### Requirement detail

* password disimpan dalam bentuk hash aman
* access token berumur pendek
* refresh token digunakan untuk memperpanjang sesi
* session lama dapat dicabut dari server

---

### 10.2 Device Registration & Pairing

Cloud harus mendukung:

* register device baru
* generate pairing code / QR
* mengikat device ke user tertentu
* revoke device
* melihat daftar device milik user
* mencatat last seen device

#### Requirement detail

* satu device memiliki identitas unik `device_id`
* pairing hanya bisa dilakukan jika pairing token valid
* pairing token memiliki masa berlaku
* device dapat dipindahkan ke akun lain hanya jika dilepas secara sah

---

### 10.3 Data Ingestion

Cloud harus mampu menerima data dari:

* aplikasi pengguna
* Raspberry Pi local backend
* service internal

#### Requirement detail

* semua request data harus punya `request_id` / `event_id`
* endpoint ingest harus idempotent
* payload disimpan sebagai raw JSON dan normalized data bila perlu
* sistem harus mendukung retry tanpa duplikasi

---

### 10.4 Sync Service

Cloud harus mampu:

* menerima data pending dari local backend
* menyimpan status sync
* mengembalikan acknowledgement
* menangani konflik data
* memproses data bertumpuk dari mode offline

#### Requirement detail

* data sync harus bisa batch upload
* data yang gagal diproses masuk ke retry queue
* status sinkronisasi minimal: `pending`, `processing`, `synced`, `failed`, `conflict`

---

### 10.5 AI Gateway

Cloud harus menyediakan jalur untuk request AI berbasis cloud.

Fungsi:

* menerima request dari app atau device
* meneruskan ke provider AI eksternal bila online
* menyimpan metadata request dan response
* menyiapkan fallback bila service unavailable

#### Requirement detail

* request AI harus diproteksi token
* hasil AI disimpan sebagai riwayat jika diperlukan
* sistem harus dapat menolak request bila quota / akses tidak memenuhi syarat

---

### 10.6 Notification System

Cloud harus dapat mengirim notifikasi untuk:

* device berhasil pairing
* device offline terlalu lama
* sync gagal
* ada hasil analisis baru
* quota menipis
* ada perubahan status sistem

#### Channel

* in-app notification
* push notification
* email (opsional)

---

### 10.7 Monitoring, Logging, Audit

Cloud harus mengumpulkan:

* log API
* event user
* event device
* telemetry device
* error service
* audit trail perubahan data penting

#### Requirement detail

* semua event penting dicatat
* admin dapat melakukan pencarian log
* log harus mengandung timestamp, actor, device_id, request_id

---

### 10.8 Admin Management

Cloud harus menyediakan panel admin untuk:

* melihat user
* melihat device
* melihat status sync
* revoke device
* inspect log
* memonitor beban sistem
* mengelola konfigurasi global

---

## 11. Non-Functional Requirements

### 11.1 Security

* TLS wajib untuk semua komunikasi
* token harus signed dan diverifikasi
* access control berbasis role dan ownership
* endpoint sensitif harus rate limited
* request dari device harus diverifikasi
* data penting harus terenkripsi at-rest jika memungkinkan

### 11.2 Reliability

* service harus tahan retry
* data tidak boleh hilang saat koneksi drop
* sync harus idempotent
* sistem harus meminimalkan single point of failure

### 11.3 Scalability

* arsitektur harus bisa dikembangkan dari monolith rapi ke modular services
* database harus mendukung pertumbuhan user, device, dan event log
* job queue harus memproses data secara async

### 11.4 Performance

* response auth dan device lookup harus cepat
* sync batch harus efisien
* query database harus dioptimalkan dengan index yang benar

### 11.5 Maintainability

* kode harus modular
* API terdokumentasi
* schema database versioned
* migrasi terkontrol

### 11.6 Observability

* metrics, logs, tracing harus tersedia
* health check endpoint harus ada
* status service harus bisa dilihat admin

## 14. Authorization Model

Cloud backend harus membedakan beberapa level akses:

### Roles

* **Super Admin**: akses penuh
* **Admin Operasional**: monitoring, revoke, support
* **User**: akses data miliknya sendiri
* **Device Service**: akses terbatas untuk device terdaftar

### Prinsip

* user hanya boleh melihat data miliknya
* device hanya boleh mengirim data yang sesuai ownership
* admin dapat melakukan override dengan audit lengkap

---

## 15. Pairing & Trust Model

Cloud harus memegang otoritas untuk menentukan trust.

### Flow pairing yang disarankan

1. User login ke cloud.
2. Device menampilkan QR dengan `device_id` + pairing token sementara.
3. App memindai QR.
4. App mengirim pairing request ke cloud.
5. Cloud memverifikasi device token.
6. Cloud mengikat device ke user.
7. Cloud mengeluarkan credential/konfirmasi pairing.
8. Device dan app menyimpan credential untuk mode offline berikutnya.

### Prinsip penting

* jangan bikin identitas baru secara lokal jika belum pernah bootstrap
* offline hanya boleh reuse identity yang sudah disahkan cloud sebelumnya

---

## 16. Sync Strategy

### 16.1 Prinsip Sync

* local backend menyimpan data dulu
* cloud menerima saat tersedia
* setiap item sync punya ID unik
* sync harus aman dari duplikasi
* cloud bisa menolak data yang tidak valid

### 16.2 Status Sync

* `pending`
* `queued`
* `sending`
* `synced`
* `failed`
* `conflict`

### 16.3 Conflict Resolution

Pilihan strategi:

* **last write wins** untuk data sederhana
* **version-based merge** untuk data yang lebih sensitif
* **manual review** untuk kasus anomali

### 16.4 Retry Strategy

* retry otomatis jika gagal jaringan
* backoff eksponensial
* batas retry tertentu
* payload tetap disimpan sebelum sukses

## 21. Availability & Reliability Target

### Target minimum awal

* uptime service inti: 99.5%+

### Recovery target

## 25. Acceptance Criteria

Cloud backend dianggap siap tahap awal bila:

* user bisa register dan login
* device bisa dipairing ke user
* device punya identitas unik dan bisa direvoke
* data dari local backend bisa masuk ke cloud
* sync berjalan aman walau ada retry
* data tidak dobel saat request dikirim ulang
* cloud menyimpan data utama secara konsisten
* logging dan monitoring aktif
* admin bisa melihat status user, device, dan sync job

---

## 26. Risiko Produk

1. **Sync conflict** jika data berubah di local dan cloud bersamaan.
2. **Token leakage** jika credential device tidak aman.
3. **Data duplicate** jika idempotency tidak diterapkan.
4. **Queue menumpuk** jika internet lama mati.
5. **Cloud over-simplified** jika semua logic dipaksa masuk satu service.
6. **Observability lemah** sehingga error sulit dilacak.

---

## 27. Mitigasi Risiko

* gunakan UUID untuk semua event utama
* buat idempotency key
* simpan queue lokal sebelum kirim
* pisahkan auth, device, sync, dan data layer
* gunakan audit log dan monitoring
* siapkan retry + backoff
* desain revocation dan expiry dari awal
